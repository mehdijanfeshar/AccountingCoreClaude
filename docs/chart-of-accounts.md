## ۲. «شناوری» دقیقاً چطور مدل شده است

هستهٔ منطق شناور این است که **معین فقط «نوع» تفصیلی را می‌شناسد، نه «مقدار» آن را.**

```
SubsidiaryAccount
 └─ SubsidiaryDetailTypeLink (۰..N)
     ├─ DetailAccountTypeId      ← فقط «نوع»
     ├─ Requirement              ← الزامی یا اختیاری
     └─ DisplayOrder             ← ترتیب نمایش فیلدها در فرم صدور سند

Voucher → VoucherLine
 └─ VoucherLineDetailValue (۰..N)
     ├─ DetailAccountTypeId
     └─ DetailAccountId          ← «مقدار» واقعی، فقط این‌جا ظاهر می‌شود
```

این تفکیک صرفاً قراردادی نیست، بلکه **ساختاری** است: کلاس `DetailAccount` عمداً هیچ فیلد ارجاعی به `SubsidiaryAccount` ندارد. یعنی حتی اگر کسی بخواهد، نمی‌تواند در زمان تعریف معین یک تفصیلی مشخص را به آن بچسباند — چون چنین فیلدی در مدل وجود ندارد. این تضمینِ **قانون ۴** است.

یک معین می‌تواند هم‌زمان به چند نوع تفصیلی وصل باشد (مثلاً «حساب‌های دریافتنی» به «مشتریان» و «پروژه‌ها»)، و افزودن نوع تفصیلی جدید هیچ تغییری در ساختار کد گروه/کل/معین لازم ندارد.

### حالت «غیرمجاز» چگونه بیان می‌شود (تصمیم طراحی)

`DetailRequirement` عمداً فقط دو مقدار دارد:

```csharp
public enum DetailRequirement { Optional = 1, Required = 2 }
```

«غیرمجاز» یک مقدار سومِ enum **نیست**، بلکه از طریق **عدم وجود لینک** بیان می‌شود:

> **لینک‌نشده = غیرمجاز**

برای غیرمجاز کردن نوعی که قبلاً مجاز بوده، باید `SubsidiaryAccount.UnlinkDetailType(...)` صدا زده شود، نه این‌که مقدار enum عوض شود.

**دلیل انتخاب:** اگر `Forbidden` هم یک مقدار enum بود، دو راه مختلف برای بیان یک معنا وجود می‌داشت (رکورد لینک با `Forbidden` در برابر نبودِ رکورد)، و هر جای کد که این را چک نمی‌کرد یک باگ بالقوه بود. حذف حالت زائد، مدل را ساده‌تر و از نظر داده‌ای فشرده‌تر می‌کند. هر دو مسیر در نهایت به رفتار یکسان می‌رسند؛ منبع حقیقت `SubsidiaryDetailPolicy.IsAllowed(typeId)` است.

## ۴. قوانین اعتبارسنجی و محل enforce شدن هرکدام

| # | قانون | کجا enforce می‌شود |
|---|---|---|
| ۱ | هر سطح فقط زیر والد درست خودش ساخته شود | سازندهٔ `internal` + متدهای `AddGeneralLedgerAccount` / `AddSubsidiaryAccount` |
| ۲ | کد با طول/فرمت ثابت | `AccountCode.Create` |
| ۳ | کد تکراری در یک والد | `DuplicateAccountCodeException` در متدهای افزودن |
| ۴ | یک نوع تفصیلی دوبار به یک معین لینک نشود | `SubsidiaryAccount.LinkDetailType` |
| ۵ | در تعریف معین هیچ مقدار تفصیلی ثبت نشود | ساختاری: `DetailAccount` فیلد ارجاع به معین ندارد |
| ۶ | تفصیلی‌های **الزامی** باید مقدار داشته باشند | `VoucherLine.AttachDetailValues` + `ReValidateForPosting` |
| ۷ | تفصیلی **غیرمجاز/لینک‌نشده** رد شود | همان‌جا، از طریق `SubsidiaryDetailPolicy.IsAllowed` |
| ۸ | حداکثر یک مقدار برای هر نوع در یک ردیف | همان‌جا، با `HashSet` |
| ۹ | تطابق `DetailAccount` با نوعش | **ساختاری**: نوع مستقیماً از `DetailAccount.DetailAccountTypeId` خوانده می‌شود |
| ۱۰ | فقط یکی از بدهکار/بستانکار غیرصفر؛ هر دو صفر ممنوع | `VoucherLine.ValidateAmounts` |
| ۱۱ | مبلغ منفی ممنوع | `Money.Of` |
| ۱۲ | سند بدون ردیف Post نشود | `VoucherPostingValidator` |
| ۱۳ | سند باید در زمان Post تراز باشد | `VoucherPostingValidator` |
| ۱۴ | سند Posted تغییرناپذیر است | `Voucher.EnsureDraft` |

نکتهٔ مهم دربارهٔ قانون ۹: در طرح اولیه، `VoucherLineDetailValue` هم `DetailAccountTypeId` و هم `DetailAccountId` را به‌صورت دو ورودی مستقل می‌گرفت، و باید چک می‌شد که این دو با هم بخوانند. در پیاده‌سازی فعلی، `VoucherLine` خودِ شیء `DetailAccount` را می‌گیرد و نوع را از آن استخراج می‌کند. در نتیجه «عدم تطابق نوع» دیگر یک خطای قابل‌رخ‌دادن نیست که باید رد شود، بلکه **از اساس غیرقابل بیان است**. این ارتقای یک قانون زمان‌اجرا به یک تضمین زمان‌کامپایل است.

## ۵. تصمیم طراحی کلیدی: چطور Domain بدون دیتابیس اعتبارسنجی می‌کند

مسئله: لایهٔ Domain نباید به دیتابیس دسترسی داشته باشد، ولی اعتبارسنجی ردیف سند به «سیاست تفصیلی معین» نیاز دارد. ضمناً `Voucher` و `AccountGroup` دو Aggregate جدا هستند و طبق DDD نباید ارجاع زندهٔ مستقیم به هم نگه دارند.

راه‌حل: **هر دو مسیر با هم پیاده شده‌اند.**

**مسیر الف — جلوگیری در لحظهٔ ساخت:**
لایهٔ Application معین را از Repository می‌خواند، `GetDetailPolicy()` را صدا می‌زند تا یک `SubsidiaryDetailPolicy` (اسنپ‌شات فقط‌خواندنی و کاملاً درون‌حافظه‌ای) بگیرد، و **همان اسنپ‌شات** — نه خودِ `SubsidiaryAccount` — را به `Voucher.AddLine(...)` می‌دهد. چون تنها امضای موجود برای ساخت ردیف، گرفتن این policy است، ساختن یک ردیف نامعتبر از اساس ممکن نیست.

**مسیر ب — آخرین خط دفاعی در لحظهٔ Post:**
`VoucherPostingValidator` (در `Rules/`) درست پیش از تغییر وضعیت به `Posted` کل سند را دوباره بازبینی می‌کند.

**چرا هر دو لازم است:** EF Core هنگام بازیابی موجودیت از دیتابیس، سازندهٔ خصوصی/فکتوری دامنه را دور می‌زند و مستقیماً فیلدها را پر می‌کند. پس یک `Voucher` که از DB لود شده ممکن است هرگز از مسیر `VoucherLine.Create` عبور نکرده باشد. مسیر ب این شکاف را می‌بندد و فقط با داده‌های موجود روی خود سند کار می‌کند (بدون هیچ دسترسی بیرونی).

> **نکتهٔ مهم برای فاز Infrastructure/Oracle:** اعتبار مسیر ب به این وابسته است که `VoucherLine.DetailPolicySnapshot` واقعاً persist و بازیابی شود. `database-oracle` و `backend-dotnet` باید برای نگاشت این Value Object تصمیم صریح بگیرند؛ اگر persist نشود، اعتبارسنجی زمان Post روی موجودیت‌های بازیابی‌شده بی‌اثر خواهد بود.

## ۷. محدودیت‌های شناخته‌شده و کارهای باقی‌مانده

- `SubsidiaryAccount.FullCode` مستلزم بارگذاری کامل زنجیرهٔ `AccountGroup → GeneralLedgerAccount → SubsidiaryAccount` است؛ Repository باید همیشه این زنجیره را کامل بار کند.
- `AccountNature` در نسخهٔ فعلی فقط یک برچسب اطلاعاتی/گزارشی است و در اعتبارسنجی ردیف سند دخالت ندارد. محدودیت «فقط یکی از بدهکار/بستانکار» مستقل از ماهیت، برای همهٔ معین‌ها یکسان اعمال می‌شود.
- `DetailAccount.Code` فقط بررسی «خالی نبودن» دارد و طول/یکتایی آن enforce نشده (برخلاف `AccountCode` سطوح ثابت).
- نگاشت `DetailPolicySnapshot` به Oracle هنوز تصمیم‌گیری نشده (رجوع به هشدار بخش ۵).
- هیچ مفهوم دوره/سال مالی، ارز، یا ابطال سند (Reversal) هنوز در مدل نیست.
